## Architecture

| Layer | Choice | Why |
|---|---|---|
| App | **Next.js (App Router) + TypeScript** | Public idea pages are *shared links*. They need server-rendered OG cards and SEO — that's core to a validation product, and an SPA gives it up. Also lets the agent service live in the same deploy. |
| Styling | **Port the prototype CSS as-is** | `Design/Hatchly.html`'s `:root` tokens are already a real design system — two themes, semantic colors, motion curves. Port it verbatim. Do **not** rewrite into Tailwind; that trades a working system for churn. |
| Data | **Pluggie** (Neon) | Collections, relations, full-text, changes feed. Client generated by `get_client_code` — regenerate after every schema change. |
| Auth | **Clerk** | Already connected (`glad-phoenix-18`). Drives Pluggie owner-scoping. |
| Media | **R2** | Covers, avatars, logos. On-demand resizing for feed thumbnails. |
| Email | **Resend** | Via declarative Pluggie `events`. |
| Agent | **Next route handlers** | Streaming chat, memory extraction, artifact generation. BYOK — keys never touch Pluggie. |

**Non-negotiables**
- Raw `sk-ant-…` keys never enter a Pluggie collection. Pluggie stores
  `{provider, masked_hint, active, connected_at}`; the secret is encrypted at rest in the
  agent layer, decrypted per request, never logged, never echoed into chat context.
- Bucks are play money. Every surface that touches them keeps the existing copy:
  *"Prestige, not equity — bucks are never real money."* This is a legal posture, not a
  tone choice.
- Memory stays read-only in the UI. It changes by talking, never by editing.

## M0 · Scaffolding — *unblocks everything*  `~1 wk`

Next.js + TS repo. Design tokens ported and verified against the prototype in both
themes. Clerk wired end-to-end (sign up → session → JWT). Pluggie client generated.
Agent service skeleton with the BYOK vault. CI, envs, preview deploys.

**Done when:** a logged-in user hits a page that reads their own row from Pluggie.

## M1 · Schema  `~1 wk`

Every collection defined and seeded from `app/data.jsx` so screens have real content
from first paint.

Core: `users` · `ideas` · `chats` · `messages` · `memories` · `brief_sections` ·
`artifacts` · `activity`
Social: `feedback` · `contacts` · `demand_signals` · `quick_ideas` · `quick_comments` ·
`quick_votes`
Economy: `transactions` · `stakes` · `spotlight_bids` · `leaderboard` (derived)

Owner-scoping on everything private; `publicFilter` on anything the stream serves.

**Done when:** the seeded dataset round-trips through the delivery API with correct
visibility for anonymous, owner, and other-user.

## M2 · The agent loop — *the risk*  `~2–3 wks`

Headless. No UI. This is the part that can fail quietly, so it gets proven first.

- Chat turn → extract memories → assign `feeds` → fill brief sections
- Provenance: every memory keeps its chat, turn, and the user's verbatim words
- Tool-call traces surfaced back to the UI
- Streaming responses, BYOK key resolution, error and rate-limit handling
- **Eval harness** — a fixture set of real conversations with expected extractions

**Three failure modes to test explicitly:**
1. *Hallucinated memory* — inventing facts the user never said. Fatal to trust; memory is
   the product's spine.
2. *Over-capture* — turning small talk into memories until the tab is noise.
3. *Premature completion* — marking the brief done on thin answers, so the build gate
   opens on an idea that isn't ready.

**Done when:** replaying the fixture conversations produces stable, correct memories and
brief sections across runs.

## M6 · Economy core — *the other risk*  `~2–2.5 wks`

**Rules live in [ECONOMY.md](ECONOMY.md).** Build against that, not against the prototype —
the prototype only increments an idea's counter and never credits the founder's wallet.

Wallets, daily reward + streak, investing (backer wallet → founder wallet), the
self-investment tax, transaction ledger, cumulative project totals, and the rolling-window
rank.

Every balance move is atomic. Pluggie gives `transact` (atomic batches) and
`update_entry_if` (compare-and-set) — a naive read-modify-write will lose money under
concurrency. Balance is **derived from the ledger**, never a mutable counter that can drift.

**Abuse surface — the design must answer this, not defer it:** mutual investment between two
accounts pays no self-investment tax, so alt-account funnelling routes straight around the
main sink. See ECONOMY.md §1.

**Done when:** concurrent investment in the same idea from multiple sessions never
double-spends or loses a transaction, and ledger sum always equals wallet balance.

---

## M6b · Admin & moderation console  `~1.5–2 wks`  ← *runs with M6*

You cannot operate an economy you can't see. This ships **with** M6, not after it.

**Don't build generic CRUD** — Pluggie already has an admin console for raw data. Build only
what's specific to Hatchly:

- **Economy observability** — money supply, in vs out, sink throughput, inflation rate over
  time, wallet distribution, whale watch
- **Collusion detection** — reciprocal investment pairs, funnelling clusters, accounts whose
  inflow is concentrated in one source
- **Moderation actions** — report queue, hide/take down an idea, comment removal, suspend a
  user, reverse a transaction
- **Spotlight** — current holder, auction history, upcoming window
- **Season controls** — refresh cadence, period boundaries, archived winners
- **Audit trail** — every admin action logged

**Done when:** an operator can spot a funnelling ring and act on it without a database client.

## M8 · Spotlight auction  `~1 wk`

**Sink 2.** A winning bid is **burned**, not refunded — see ECONOMY.md. This differs from the
prototype, whose refund-on-outbid made the slot free to hold indefinitely.

Bidding, the holder banner, window expiry, and the auction reopening.

The most concurrency-sensitive surface in the product: two simultaneous bids must not both
win, and a refund to a losing bidder must happen exactly once. Build it on CAS and test it
under deliberate contention.

## Cross-cutting — *don't leave to the end*

| | |
|---|---|
| **Moderation** | Now a real milestone — **M6b**. The user-facing half (report buttons, blocked states) still needs designing into the v4 screens, which have no such affordance today. |
| **Mobile** | The prototype is desktop-first with breakpoints that shed rails. The stream and idea pages are the shared surfaces — they'll be opened on phones first. |
| **Accessibility** | Keyboard paths, focus states, contrast in both themes, `prefers-reduced-motion` (the tokens already honor it). |
| **Rate limits** | Chat costs money even under BYOK; posting and voting invite spam. |
| **Observability** | Agent traces, failed extractions, delivery outcomes (`get_deliveries`). |

## Sequencing logic

**M0 → M1 → M2 → M3** is the critical path and must be serial: nothing works until the
agent loop is proven, and the loop needs the schema.

After M3, two tracks can run in parallel:
- **Creation** — M4 artifacts, M5 publishing
- **Social** — M6 + M6b economy & admin, M7 stream, M8 auction

M9–M11 are additive and can slot around either.

**Rough total: ~18–23 weeks** for one developer to a launchable v1, admin and moderation
included.

---

## Three shippable checkpoints

1. **Private alpha** (M0–M3) — a founder shapes an idea and gets a build prompt. No
   social. Fully useful on its own, and the fastest honest test of whether the agent is
   good enough.
2. **Public beta** (+ M4–M5, M7 read-only) — ideas are publishable and shareable, stream
   is browsable, no currency yet. Tests whether people *want* to show their ideas before
   introducing money mechanics.
3. **Full v1** (+ M6, M8–M11) — the economy switches on.

Splitting it this way de-risks the biggest unknown: **the economy is the hardest part to
build and the easiest part to get wrong socially.** Checkpoint 2 tells you whether the
social layer has pull before you build the currency that's supposed to power it.
